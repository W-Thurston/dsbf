# Golden runs

A golden run profiles a dataset end to end with the `core` pack and compares its findings
with a committed snapshot. The snapshots record what DSBF reports today, so any later
change to a check, a threshold or the engine shows up as a reviewable diff instead of a
silent shift.

| Dataset | Source |
|---|---|
| `clean`, `tiny`, `near_clean`, `all_categorical`, `high_missingness`, `severe_multicollinearity`, `single_column`, `wide` | The eight archetype generators in `tests/generators`, seed 42, rebuilt on every run |
| `titanic` | `data/titanic.csv` (vendored; see `data/README.md`) |
| `kitchen5k` | `DSBFTestDataGenerator(n_rows=5000, random_seed=42)` with `normal_date` as the time-series column |
| `sms_spam` | `data/SMSSpamCollection` (vendored, CC BY 4.0; see `data/README.md`), written as a CSV with the header `label,text` |

## Run them

The suite is deselected by default (it takes several minutes, and `kitchen5k` is most of
that):

```bash
uv run pytest -m golden                  # compare every dataset with its snapshot
uv run pytest -m golden -k titanic       # one dataset
```

CI runs it in `.github/workflows/golden.yml`: nightly, on demand, and on a pull request
labelled `golden`. Add that label to any pull request that changes what a check reports.

## Review and update a snapshot

A failure prints the changed lines of the snapshot. Decide whether each change is intended:

1. Read the diff. A changed `status`, `severity` or `code`, a finding that appears or
   disappears, or a number that moves by more than the sixth significant figure, is a
   behaviour change.
2. If it is intended, accept it:

   ```bash
   uv run pytest -m golden --update-golden
   git diff tests/golden/snapshots
   ```

3. Commit the snapshot files with the change that caused them, and describe the change in
   the commit body.

Never edit a snapshot by hand: it is regenerated by `--update-golden` and nothing else.

## What a snapshot holds

`snapshots/core/<dataset>.json` holds, for each core check, its version and status and its
findings reduced to id, check, code, subject, severity and evidence metrics
(`snapshot.py`). A report-only check keeps what a reviewer judges: `quality_dimensions` and
`ml_readiness` keep the levels, the coverage and the columns each dimension flags.

`normalise.py` makes two identical runs produce identical files:

- Timings, memory figures and timestamps are dropped.
- Floats are rounded to 6 significant figures. NaN and infinities become the strings `"NaN"`,
  `"Infinity"` and `"-Infinity"`.
- Keys are sorted, and the file is written with fixed formatting.

A check that does nothing without parameters (`format_violations` runs only the rules it is
given, besides its scan for mixed date formats) gets them from `GoldenDataset.core_params`;
`sms_spam` sets the two rules its snapshots exercise. The runner passes them to
`profile_one.py` in `DSBF_GOLDEN_CORE_PARAMS`. The dataset's time-series column is passed
the way `dsbf.profile(time_index=...)` does, as the `time_index` parameter of each check
that has one (`stationarity`, `autocorrelation` and `seasonal_decomposition`); kitchen5k
is the only dataset with one.

## Determinism

Each dataset runs in a fresh child process (`profile_one.py`) with a temporary `DSBF_HOME`
and a temporary working directory, and the snapshot is built from that run's own `Run`.
No check depends on the order of a set of strings, so the hash seed is not pinned: the
`fuzzy_duplicates` check gives the same output under every seed
(`tests/test_checks/test_fuzzy_duplicates.py` runs it under three).
A snapshot can still differ across platforms or major library versions (BLAS builds,
scikit-learn and SciPy releases); when CI disagrees with a local run, compare the diff before
updating.
