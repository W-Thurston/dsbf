# Golden runs

A golden run profiles a dataset end to end and compares the result with a committed
snapshot. The snapshots record what DSBF reports today, so any later change to a task, a
threshold or the engine shows up as a reviewable diff instead of a silent shift.

| Dataset | Source |
|---|---|
| `clean`, `tiny`, `near_clean`, `all_categorical`, `high_missingness`, `severe_multicollinearity`, `single_column`, `wide` | The eight archetype generators in `tests/generators`, seed 42, rebuilt on every run |
| `titanic` | `data/titanic.csv` (vendored; see `data/README.md`) |
| `kitchen5k` | `DSBFTestDataGenerator(n_rows=5000, random_seed=42)` with `normal_date` as the time-series column |
| `sms_spam` | `data/SMSSpamCollection` (vendored, CC BY 4.0; see `data/README.md`), written as a CSV with the header `label,text` |

## Run them

The suite is deselected by default (it takes about ten minutes, and `kitchen5k` is most of
that):

```bash
uv run pytest -m golden                  # compare every dataset with its snapshot
uv run pytest -m golden -k titanic       # one dataset
```

CI runs it in `.github/workflows/golden.yml`: nightly, on demand, and on a pull request
labelled `golden`. Add that label to any pull request that changes what a task reports.

## Review and update a snapshot

A failure prints the changed lines of the snapshot. Decide whether each change is intended:

1. Read the diff. A changed `status`, `guidance` title or `level`, a task that appears or
   disappears, or a number that moves by more than the sixth significant figure, is a
   behaviour change.
2. If it is intended, accept it:

   ```bash
   uv run pytest -m golden --update-golden
   git diff tests/golden/snapshots
   ```

3. Commit the snapshot files with the change that caused them, and describe the change in
   the commit body.

Never edit a snapshot by hand: it is regenerated by `--update-golden` and nothing else.

## What a snapshot holds

`snapshots/<dataset>.json` has the run's shape, inferred stage, sampling and task outcomes,
the `top_ml_risks` list, and for every task its `status`, `summary`, `data`, flattened
`guidance` (path, phase, column, level, title), `reliability_warnings`, `recommendations`,
`ml_impact_score` and `error`.

The normaliser in `normalise.py` makes two identical runs produce identical files:

- Timestamps, durations and memory figures are dropped. The two tasks that only measure time
  and memory (`identify_bottleneck_tasks`, `log_resource_usage`) keep just their status.
- Output and temporary directories become `<run>`.
- Floats are rounded to 6 significant figures. NaN and infinities become the strings `"NaN"`,
  `"Infinity"` and `"-Infinity"`.
- Keys are sorted, and the file is written with fixed formatting.
- A result too large to read in a diff (a list or dict of more than 40 entries, or a nested
  structure over about 2,000 characters) is replaced by `{"_len": n, "_digest": "<sha1>"}`.
  Any change to it still fails the comparison, but the diff shows only the digest. To see
  what changed, profile the dataset with `dsbf profile` and compare the two reports.

## The same datasets through the new engine

`test_engine_parity.py` runs each dataset through the new engine (`engine_one.py`: load,
profile, every adapted legacy task through `execute`, with the pandas backend the legacy
engine used for files) and compares each task with the snapshot, using the snapshot's own
normaliser. The snapshots come from the legacy engine, so the two differ in places;
`engine_differences.json` lists every difference by dataset and task, and a run that
differs in any other way, or no longer differs where it did, fails.

A difference is one of two kinds. `status: legacy success, engine not_applicable` is a
task the engine plans `not_applicable` because the profile types no column the way the task
expects. `changed: data, summary` names the entry fields that moved. The snapshot's `"NaN"`
is read as the null a result holds, so that is not a difference. `changed` in the file
gives each changed task a reason (`types`, `load` or `downstream`, defined in `reasons`).

After a change that moves a difference, read it and rewrite the file:

```bash
uv run pytest -m golden -k engine --update-golden
git diff tests/golden/engine_differences.json
```

Give a task that now differs under `changed` a reason by hand: the update writes the
differences and leaves `changed` and `reasons` alone.

## The core pack on the same datasets

`engine_one.py` also runs the `core` pack alone and writes its `Run` as `core_run.json`.
Two suites read it, sharing one child run per dataset (`conftest.py`).

**Core findings snapshots.** `snapshots/core/<dataset>.json` holds, for each core check,
its version and status and its findings reduced to id, check, code, subject, severity and
evidence metrics (`migration/snapshot.py`). `test_core_snapshot.py` compares and rewrites
with `--update-golden`, like the legacy snapshots. Commit the files with the change that
moved them and explain the diff in the PR.

**Migration parity.** `test_migration_parity.py` compares each core check with the legacy
task it replaces (`dsbf.legacy.SUPERSEDED_BY`), using the task's result through the adapter
in `engine_run.json`. The task's comparator (`migration/<check>.py` or
`migration/column_health.py`, listed by task name in `migration/registry.py`) returns the
differences: columns each side reads, counts, shares, severities and the findings each
raises. Two tasks can share a core check, and each is judged against its own entries. Every
difference must be in `migration/accepted.py` with the task, the column, the kind, the exact
detail and the reason the core check is right; one that is not listed fails, and so does a listed one that no longer
occurs. The failure prints the entry to add. Reasons are written by hand, so
`--update-golden` leaves the file alone. A unit test checks that every entry has a reason
and names a golden dataset and a registered comparator.

To migrate another task, add it to `SUPERSEDED_BY`, write its comparator, run the suite,
and list each difference with its reason.

A core check that does nothing without parameters (`format_violations` runs only the rules it is
given, besides its scan for mixed date formats) gets them from `GoldenDataset.core_params`;
`sms_spam` sets the two rules its snapshots exercise. The runner passes them to
`engine_one.py` in `DSBF_GOLDEN_CORE_PARAMS`, and only the core run uses them.

## Determinism

Each dataset runs in a fresh child process (`profile_one.py`) with `PYTHONHASHSEED=0`, a
temporary database and a temporary working directory, and the snapshot is built from that
run's own `report.json`. The hash seed is needed because some tasks walk sets of strings.
`fuzzy_duplicate_detection` stops at a candidate cap while doing so, so without the seed it
reports a different pair count on every run (titanic gave 7,102 and 20,029 on two runs).
A snapshot can still differ across platforms or major library versions (BLAS builds,
scikit-learn and SciPy releases); when CI disagrees with a local run, compare the diff before
updating.
